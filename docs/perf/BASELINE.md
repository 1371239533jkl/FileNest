## 2. 结论

1. **B7（每语句 commit）成立，但不是"放大器"级问题**：WAL 下单行仅 0.02ms（批量 33×）；经应用层 DAO 实测（含 FTS5 触发器与唯一索引）为 **0.18ms/行 → 0.052ms/行，约 3×**。真正的每行成本来自 FTS 触发器，而不是 commit 本身。
2. **B10（纯 Python 余弦）需修正量级**：1 万条约 0.42s，不是此前文档描述的"秒级"。距 50ms 目标需 8×，numpy 矩阵化 + 缓存预期远超此值。
3. **B9（O(n²) 分组）确认**：1 万张约 10.6s，需 26×；numpy 分块 XOR 可达，但必须做对拍（结果与纯 Python 一致）。
4. **深分页当前不是痛点**：5 万行下深页 0.60ms，仅首页的 15×（绝对值仍 <1ms），用户无感。keyset 分页是为 10 倍增长预留，**不应作为救火项或卖点**。
5. 扫描/哈希为**热缓存下的 CPU 上限**，冷盘会显著更低；数值只能同机前后对比，不能跨机引用。

### 2.1 计算内核（T1-6，2026-11-18）

22,000 文件 / 164MB / 12 核机器，`bench/run_compute.py`：

| 项 | 旧/串行 | 新/并行（8 进程） | 倍率 |
|----|---------|-------------------|------|
| 目录遍历 | 0.119 s（`os.walk` + 每文件 `os.stat`） | 0.073 s（单次 stat 取全属性） | **1.64×** |
| SHA-256（冷缓存） | 12.18 s（13.5 MB/s） | 0.86 s（192 MB/s） | **14.2×** |
| SHA-256（热缓存） | 1.36 s（121 MB/s） | 0.62 s（266 MB/s） | **2.2×** |
| 并行**遍历** | 0.073 s | 0.254 s | **0.29×（已删除）** |

结论：

- 多进程只对**哈希**有效：冷盘首次扫描 14×，重复扫描（页缓存命中）2.2×，均达到 ≥2× 目标。
- 遍历加进程是负收益（22k 文件仅 73ms，Windows 进程池启动 ~200ms），已移除并行遍历代码；改为"每个文件只 stat 一次"，稳定 1.64×。
- `map(chunksize=64)` 比 `chunksize=8` 快约 30%（减少跨进程往返），对小文件场景必要。

## 4. 复现


## 5. 口径与限制

- 单机单次会话；扫描/哈希取 3 次中位数，数值型指标（余弦、分组）资源占用高，仅 1 次。
- 数据集由全零字节构成，只影响压缩/去重语义，不影响遍历、哈希与 SQLite 计时。
- 指标采集代码不 import 项目模块（`core/` 会拉入 PyQt6），属"原始能力"口径，非应用端到端。
